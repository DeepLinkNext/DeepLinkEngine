# 参考算力标定与复算

## 默认一键认证

正常评测使用仓库根目录的 `one_click.py run --config evaluation.json`，自动在模型评测退出后执行本轮参考认证。已有封存五项性能批次使用 `one_click.py --compute-reference-only --reference-campaign ...`；完整命令与显式封存阶段接续见[主入口说明](../README.md)。用户无需另备下面专家接口使用的现场参考计划。

默认参考工况按 Topic4 V2 固定200题、max256、保留EOS，每臂三次正式原生测量。规范参考统计在目标正式计时前冻结；每臂先求和三轮算量、参考下界与原生时间，再计算比值。固定五项性能评测的预算保持原契约；`--reference-profile full-answer-v1` 另行使用 max8192、每臂一次，单独报告。

自动流程按原生B0/B1各自的公开DELTA结果，建立目标模型、必要草稿生产者、注意力、GDN、卷积和标量的完整必要算量区间。独立HTTP补充观测只验证已加载源码与生产者适用域，不能把其时间或输出数量移入原生计时。参考部分使用恢复的原始规范dense程序、种子137、3次预热、每重复20次图预热、5组各100次回放，以及原数值门槛；按当前源码形状重新标定，不复用历史加权数量或耗时。

现有dense末段下界图只保留部分算子。它不能替代本项目已确认的完整独立参考，不触发完整认证或50%/90%判定。此前将该图提升为完整认证的行为已撤回。完整参考必须覆盖必要计算、搬运、通信、同步和主机处理；只有源码允许的执行分支不确定性可以按原方法保留界，不能以尚未接入的整类算子作为完成认证的依据。

默认 `submission-v2` 自动恢复并复算已封存完整M01参考的原始F、独立关键路径参考时间与每卡上界。先核验全部来源，再匹配本轮完整token清单、14分片权重、精度、TP2、910B2、每臂三轮及200题/max256/原生计时边界。该参考分母在本轮计时前已独立固定；所有本轮分子重新计算，不使用历史百分数。复用域见[机器协议](../protocols/m01-full-reference-reuse-domain-v1.json)。

```text
C本轮下界 = ΣF本轮下界 / (2 × ΣT本轮 × 10¹²)
C参考上界 = ΣF原参考上界 / (2 × ΣT原参考下界 × 10¹²)
η下界 = 100 × C本轮下界 / C参考上界
```

两份F分别保留；不同F不能相消为时间比。本轮原件、完整参考原件、适用性审计、六轮计时与分子复算全部归档后，才输出 `qualified_full_reference_denominator_reuse/v1`。缺项、预算不符或原件改变时非零退出；部分dense结果仅为诊断，旧认证身份已撤回。out8192完整回答仍单列，不能复用out256参考分母。

异步 HTTP 路径的 CPU 草稿槽可能记录 `-1`，调度位置也可能是推测拒绝前的估计。独立复算按冻结源码、两卡真实草稿输出、当前设备输入、保留输出及实际位置建立派生输入视图；只有立即前一轮的同请求生产者才可解析占位值。冻结 r8 的第二步长度发布由 `causal_draft_lengths.py` 在 FIA 读取前执行，复算核验发布前后设备值与选中位置，只接受这一项来源明确的变化。原始流和失败回执保持不变。采集必须已正常关闭、两卡编译边界完整且全部200响应通过独立审计，才可在新目录接续 CPU 认证；缺失关闭记录或未结束的服务不能恢复为成功。来源口径见[异步设备输入协议](../protocols/async-http-device-input-source-domain-v1.json)。

## 专家现场接口

以下为另行冻结现场计划的原始接口，其整链验证要求仍适用于该接口。默认自动流程采用上面的完整必要工作与有证明的参考下界口径。

## 在现场采集并出图

适用于 3.4.1 有效算力。按已冻结的工况准备下面的输入后，从 Linux Ascend 执行环境运行一次。输出目录须为新目录。

```bash
python3 run_vllm_hust_tests.py run-live-reference --plan execution-plan.json --sha256 "$PLAN_SHA256" --out m01-run-001
```

如果同一份清单已冻结其余测试项，使用 `run` 运行整份清单，其中 3.4.1 使用相同的现场采集流程。

### 冻结本工况输入

| 输入 | 按模板准备 |
| --- | --- |
| `live-workload.example.json` | 实际测量及预热请求的 token ID、请求顺序、采样参数。 |
| `reference-method.example.json` | 独立参考实现标识、工作负载文件 SHA-256、标定与验证的样本数、允许波动和整链验证误差。关键路径法使用 `critical_path`。采用全链法需已有经确认的独立整链参考口径。 |
| `live-reference.example.json` | 受测和独立参考的解释器绝对路径、运行时身份、现场采集模块、两张实卡及对应逻辑卡、阶段超时、参考适用依据。关键路径法另冻结算子名称及类别。 |
| `deployment.example.json` | 两臂实际引擎和权重身份、精度、并行配置。使用包内适配器时，`llm` 填实际部署的 `vllm.LLM` 参数，包括 `model` 和 `tensor_parallel_size: 2`。独立参考的参数放入采集配置的 `reference_config.llm`。 |
| `execution-plan.example.json` | B0、B1 的 `reference_method` 和 `live_capture` 路径，以及各输入和脚本相对路径对应的 SHA-256。 |

### 接入现场采集模块

默认的 `native_m01_accounting.py` 在实际 vLLM 调度器和两张 Ascend 卡的 worker 中记录每步请求、调度位置、已调度草稿数量、保留输出、GDN 元数据和设备时间线。脚本按运行标识关联三处日志，核验请求覆盖与实际保留的 token，并复算已覆盖的目标模型矩阵算量。

冻结部署时提供 `implementation_files`，键为现场源码文件的绝对路径，值为文件 SHA-256。适配器使用进程内 EngineCore 和两个独立的设备 worker。须在部署中明确记录 `m01_in_process_engine: true`。正式计时仍保留 CPU 侧记账成本，设备 profiler 只在单独的路径观察阶段开启。

当前可独立采集本轮证据。对于仅采集的清单，参考侧部署、标定门槛和参考身份可暂空，工作负载 SHA-256 仍须固定。受测运行身份可以在此阶段记录到 `runtime-identity.json`，用于之后冻结校验。

```bash
python3 run_vllm_hust_tests.py capture-live-work --plan execution-plan.json --sha256 "$PLAN_SHA256" --out m01-observed-001
```

每轮保存 `scheduler-waves.jsonl`、`rank-*-waves.jsonl`、`rank-*-device-trace.json`、`necessary-work-coverage.json`、`request-wave-order.json` 和 `device-dependencies.json`。设备流内顺序与观测到的 trace flow 均保留，跨 rank 的 HCCL 配对和缺失边仍需基于实际算子及通信证据认证。

正式出图需在 `target_certifier` 和 `reference_certifier` 固定工况认证实现。现有包未完成 GDN 全量算术、标量和卷积、保留草稿生产者闭包，以及规范参考算子的形状映射和跨流跨卡依赖认证。认证模块的 `certify(llm, config, phase, output, outputs, partial)` 从当前阶段原始记录返回完整 `components`、`work_identity`、`schedule_signature`、`covered_families`，关键路径法的路径观察阶段同时返回按拓扑排列的 `nodes`。覆盖字段为 `projection`、`full_attention`、`vocabulary`、`scalar`、`convolution`、`gdn_prefill`、`gdn_decode`、`draft_dependency`。认证模块按实际工况验证某项为零后，仍须记录其覆盖。参考模块的 `run_operation(llm, config, name)` 在实卡上运行独立标定。缺少正式认证时，`run-live-reference` 在启动前报缺项，不会将分项算量或设备时间线用作参考值。

脚本依次完成独立标定、独立整链验证、受测路径观察、单独的双卡同步计时。路径观察与正式计时使用相同冻结配置，逐请求输出 token、长度、终止原因以及必要工作台账必须一致。如出现无法辨明的路径分支，当前接口需要适用的完整台账才可出判定。

所有原始记录和派生回执都写入同一轮目录。参考方法和适用域一致时，脚本合并同组本轮的两臂标定样本重新计算，两臂共用参考值。两臂实际必要工作和参考适用路径有差异时，分别计算。现场入口只接受本轮创建的测量记录。

## 回执及证据

`receipt.json` 记录 `run_id`、实际物理卡 `cards` 和以下证据的相对路径。脚本从证据读取数值并复算。回执带有预填的 `reference_tflops_per_card` 或 `reference_s` 时，该组无法判定。

| 角色 | 所需记录 |
| --- | --- |
| `effective_config` | 两臂的生效配置和运行身份 |
| `work_ledger` | `run_id` 及按既定计数规则导出的 `components`，每项有 `component` 和整数 `effective_flops` |
| `timing` | `run_id`、`measurement_method` 和同步整轮的起止时刻 |
| `calibration` | `reference_id`、`cards`、`effective_flops`。关键路径法的 `operations` 每项含 `operation`、`kind`、`observations`。整链中位法使用 `whole_chain_observations` |
| `whole_chain` | `reference_id`、`cards`、`effective_flops`、独立的 `validation_observations`。关键路径法还需 `nodes`，每项含 `id`、`operation`、`predecessors`、`resources`，按原资源执行顺序拓扑排列 |
| `reference_review` | `reference_id`、`cards`、`passed` 布尔值、`basis`，关联独立性、参考实现、工作量对应和原始证据 |

这五种结构化证据均含 `workload_sha256` 和 `work_signature_sha256`，用于绑定冻结负载及必要工作。每次采集记录 `measurement_id`、整数 `start_ns`、`end_ns`。同步整链记录另含 `cards` 及 `synchronized: true`。保留独立标定、完整执行链和独立验证的原始采样，关键路径法的 `kind` 覆盖 `compute`、`memory`、`communication`，必要时含 `control`。同一测量不能同时承担实测、标定或独立验证。

脚本从起止时刻计算时长，从工作台账求有效 FLOPs，再按冻结方法计算参考时间。关键路径法用标定样本中位数给节点定时，对依赖和资源占用求关键路径。整链中位法取独立参考实现的同工况同步测量中位数。两种方法均核验独立整链观测的误差。查看 `report.html`、`summary.json` 和 `charts/effective-compute.png`。正式判定按已冻结的工况、证据和里程碑门槛执行。失败保留现场日志和已有证据。
